# Internationalization

Powered by **next-intl 4**, configured **without URL prefixes** — the site
intuits the language instead of using `/en` or `/es` paths.

- Base language: **English** (`en`). Only translation: **Spanish** (`es`).
- Supported locales live in `src/i18n/config.ts`.

## How the language is chosen

`src/i18n/request.ts` delegates to `detectRequestLocale()` (`src/lib/locale.ts`),
driven by admin **locale settings** (`getLocaleSettings`, key `locale`):

- **Single mode** → the whole site is forced to one chosen language.
- **Multi mode** → resolution priority among the **enabled** locales:
  1. `NEXT_LOCALE` cookie (a manual switch via the language switcher).
  2. The signed-in account's saved `language` (see below).
  3. The browser's `Accept-Language`.
  4. The configured fallback.

Admins control all of this at **`/admin/system/languages`** (the
`LocaleSettingsForm` at the top): single vs. multi, which languages are enabled,
and the default. The resolved locale is applied in `src/app/layout.tsx`.

### Account language

`User.language` is stamped with the active locale **when the account is created**
(in the better-auth `databaseHooks.user.create.before` hook). It acts as a
detection signal (priority 2 above) and is updated when a signed-in user picks a
language. `language` is an `input: false` additional field — set by the server,
never by the client.

### Language switcher

A **navbar item** (`type: "language"`, enable/disable like any other item). It
renders `LanguageSwitcher` (`src/widgets/navbar/`), only when more than one locale
is enabled. Choosing a language calls `setLocaleAction` (writes the cookie +
updates the account) then refreshes. Widget *content* stays single-language
(stored in config); the switcher re-translates the next-intl **chrome**.

## Messages

JSON files in `src/messages/<locale>.json`, grouped by namespace
(`common`, `auth`, …). **Every key must exist in both `en.json` and `es.json`.**

These are the **base** copy. Admins can override any string live from
**`/admin/system/languages`**; overrides are stored in the DB (one
`system_setting` row per locale, `translations:<locale>`) and merged over the
base by `buildMessages()` (`src/lib/translations.ts`) in the i18n request config.
To change the default wording in code, edit the JSON; to tweak copy at runtime,
use the admin editor.

## Using translations

Client or server components:

```tsx
import { useTranslations } from "next-intl";
const t = useTranslations("auth.login");
<h1>{t("title")}</h1>;
```

## Translatable widget & navbar content

Admin-authored content (widget headings/banners/buttons, navbar item labels) is
**per-locale**. A text field is a `LocalizedText` = `string | Record<locale, string>`
(`src/widgets/i18n.ts`): a plain string is the same for every language (legacy),
an object holds one value per locale. Lists (contact points/topics) use
`LocalizedList` the same way.

- **Render:** `resolveText(value, locale)` / `resolveList(value, locale)` pick the
  active locale, falling back to any available value. Server renders read
  `getLocale()`; client renders read `useLocale()`.
- **Edit:** the widget editor shows **language tabs** (one per *enabled* locale)
  at the top (`WidgetEditorScreen` + `LocaleContext`). Each text field reads/writes
  the value for the selected tab via `useLocalized()` (`g`/`s` for text, `gl`/`sl`
  for lists). Non-text settings (colors, layout) are shared across locales.
- **Base/legacy values:** a plain string is treated as the **default locale**'s
  value, so the **default language must match the language existing content is
  written in** (set it under Languages → "Default language"). For a Spanish-first
  site, set the default to `es` so the Spanish base is preserved when you add
  English translations.

Only the *content* is per-locale; widget **chrome** (form field labels, buttons)
still comes from next-intl messages.
